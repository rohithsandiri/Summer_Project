Abstract—Automated Kubernetes rollback systems typically detect an SLO violation in one service and roll that one service back. This leaves a real gap unaddressed: when services are released together, rolling back only the failing one strands its callers on an API contract the rollback just removed. We present a self-healing operator that (1) extends single-service automated rollback to dependency-aware batch rollback across co-released services, using a dependency graph that is itself self-maintaining — generated by statically scanning source code and continuously merged with relationships observed live via distributed tracing; (2) replaces pod-health-only recovery verification with a two-signal check (pod health and confirmation that the triggering SLO alert has actually cleared), applied uniformly to the primary rollback and to every co-released peer; and (3) extends rollback-safety discipline to the healer's own persistent state, via versioned database migrations and a startup guard that refuses to run against a schema it does not understand. Iterative live fault injection against a real cluster, cross-checked with static analysis and Go's data-race detector, surfaced twelve cross-layer defects (F1–F12) spanning Prometheus query semantics, Helm release-history ordering, Alertmanager label precedence, concurrency, and execution-gate races — several newly found during this project's own retrospective review, including one, reported here for the first time, in which the operator's own target-selection logic can re-select an already-failed revision on a repeated verification failure. A preliminary MTTR case study (explicitly scoped at one to two repetitions per scenario) reproduces the detection-latency-dominated recovery pattern reported in related single-service work. Consistent with that pattern, we report what remains open — an unparallelized peer-verification path, an in-memory-only trace store, a timestamp-based proxy for "released together," and the newly found double-rollback edge case — as directly as what was fixed.

Index Terms—Self-healing systems, Kubernetes, dependency-aware rollback, autonomic computing, site reliability engineering, mean time to recovery, Helm, Prometheus, service dependency graph, database migration safety.

I. Introduction

Automated remediation — infrastructure that detects a fault and repairs it without a human — is a long-standing goal of autonomic computing [1], [2] and a recurring feature of Kubernetes operators built around the reconcile/act loop [4], [9]. A common and effective instance of this idea watches Prometheus-based SLO alerts [8] and, on a breach, rolls a Helm release back to its previous state. Existing treatments of this pattern — including practitioner accounts benchmarked carefully against a human baseline — model the unit of recovery as a single service: one alert, one release, one rollback.

That model has a hole in it. Microservice systems are rarely deployed one service at a time; a callee's new endpoint and the caller that starts using it are routinely released together. If the callee later breaks and is rolled back alone, its still-upgraded callers are left calling a contract that no longer exists — the incident is "resolved" by the healer's own bookkeeping while the system keeps failing downstream. No published self-healing-rollback treatment we are aware of addresses this directly: the operator pattern literature [4], [9] describes reconciling one custom resource at a time, and the SRE and chaos-engineering literature [5], [6] treats remediation actions, not remediation scope, as the object of study. Separately, the trace-based service-dependency-graph literature developed for root-cause analysis [15], [16] answers "who calls whom" but has not, to our knowledge, been wired directly into a rollback-scoping decision.

This paper builds and evaluates a system that closes that gap, and — following the discipline that measurement in this space should include negative and preliminary results, not just capability claims — reports its own limitations with the same rigor as its fixes.

A. Research Questions

RQ1: Can automated rollback be extended safely beyond a single failing service to the set of services co-released with it, without amplifying blast radius or introducing the oscillation that naive multi-service rollback risks? RQ2: Does verifying against the violated SLO — rather than pod health alone — change the observed correctness of automated rollback, and does that requirement hold uniformly for peer rollbacks as well as the primary one? RQ3: What does iterative live fault injection, combined with static analysis and race detection, reveal about defects in a multi-service self-healing pipeline itself, and do these defects cluster around identifiable, recurring patterns? RQ4: For the failure modes we can directly measure, does automated rollback's MTTR advantage follow the same detection-latency-dominated pattern reported for single-service systems, and what does that imply for where to invest further engineering effort?

B. Contributions

(1) A dependency-aware batch-rollback coordinator that extends single-service automated rollback to co-released service batches, gated by an atomic per-service execution lock that we show is necessary to prevent cross-service oscillation. (2) A self-maintaining dependency graph combining static source-code analysis (a purpose-built scanner, presented here) with live trace-derived edges, replacing a hand-maintained edge list that we show was already stale — missing two real production call paths — at the moment it was audited. (3) SLO-aware, two-signal verification applied uniformly to the primary rollback and every batch-peer rollback, closing a false-success failure mode for peer rollbacks analogous to one already known for primary rollbacks. (4) The first treatment, to our knowledge in this line of work, of rollback safety for the healer's own persistent state — a versioned, forward-only migration system with a startup compatibility guard — alongside a code-grounded finding that the healed services themselves are stateless and rollback-safe by construction. (5) A catalogue of twelve cross-layer defects (F1–F12) found via live fault injection, static audit, and race detection, including a newly identified double-rollback edge case in target-selection logic. (6) A preliminary, honestly-scoped MTTR case study with an explicit replication plan.

II. Background and System Model

The system is a MAPE-K instance [1], [2]. Monitor: Prometheus scrapes the API gateway and three business microservices (order, inventory, payment) every 15 s. Analyze: PrometheusRule expressions evaluate error-rate, latency, zero-healthy-pod, and stuck-rollout conditions per service, each with an explicit for: duration, and burn-rate/error-budget engines assess severity. Plan: a policy engine matches the firing alert to a cooldown-gated recovery policy; a decision engine combines SLO state, burn rate, and root-cause signals into a confidence-scored recovery plan. Execute: a Helm-Go-SDK executor performs the rollback, followed — this paper's central extension — by a dependency-aware batch-rollback coordinator that considers co-released peers. Knowledge: policy configuration, the dependency graph (Section IV-A), and a Postgres-backed incident/decision/rollback audit trail (Section IV-D) persist across restarts.

The action path is Alertmanager-webhook-triggered, not reconcile-loop-polled: Prometheus already evaluates every SLO expression on its own schedule, and a second, independently-timed poll would duplicate that evaluation and add its own interval to every incident's MTTR. Alertmanager's own grouping latency (10 s group_wait on the critical route) is the only added delay between detection and the operator receiving the event.

III. Related Work

A. Autonomic and Self-Healing Systems

The vision of self-configuring, self-healing systems was articulated by Kephart and Chess [1] and formalized as the MAPE-K loop in IBM's autonomic-computing blueprint [2]; Psaier and Dustdar [3] survey the resulting body of self-healing approaches. Our system is a concrete MAPE-K instance in which the Plan/Execute stages now scope their action to a set of resources rather than one, which is, to our knowledge, less explored in this literature than the single-resource case.

B. Cloud Orchestration and the Operator Pattern

Kubernetes descends from Google's Borg and Omega [4] and exposes control through the operator pattern [9]. Our rollback-operator follows this pattern but, unlike a controller that reconciles one custom resource, its Execute stage must reason about a graph of resources at rollback time — a scoping problem the operator-pattern literature does not by itself address.

C. Reliability Engineering and Resilience Testing

Google's site-reliability practice [5] contributes the golden-signal alerting and error-budget framing this system adopts; MTTR is one of the four DORA delivery-performance metrics [7]. Chaos engineering [6] injects faults to expose weaknesses; we inject faults for a related but distinct purpose — verifying that a multi-service remediation pipeline behaves correctly under sustained, adversarial, real alert traffic, not only that a demo scenario completes.

D. Observability, Microservices, and Delivery

The system rests on Prometheus-based monitoring [8] and observability practice [12] over a microservice architecture [10], [11] delivered through continuous-delivery pipelines [13]. These works establish the mechanisms this system composes.

E. Trace-Based Dependency-Graph Construction

Production root-cause-analysis systems build the service call graph dynamically from observed traffic rather than a declared topology: Microscope [15] and MicroHECL [16], the latter deployed at Alibaba, construct a live causal/call graph from traces each analysis cycle. Cilium Hubble [17] takes an alternative, kernel-level (eBPF) approach, building a service map from every observed connection with no application-level instrumentation. We adopt the trace-based technique — via Jaeger's own dependency-aggregation API — for a different purpose than root-cause ranking: scoping which services a rollback should also touch, not which service caused the incident. Section VIII discusses eBPF-based discovery as a complementary future direction, since it does not share our live graph's dependence on trace sampling and storage retention (Section VII-C).

F. Database Schema Evolution

The expand/contract discipline this system applies to its own audit-trail schema — never dropping or renaming a column in the same change that stops using it — follows established evolutionary-database-design practice [19]. We are not aware of this discipline being applied specifically to a self-healing system's own state, as distinct from the state of the services it heals.

G. ML/LLM-Based Auto-Remediation

Recent work increasingly applies large language models to remediation itself — for example, generating and executing Ansible playbooks in response to microservice anomalies [18]. That line emphasizes remediation capability; our contribution is orthogonal and, we would argue, complementary: correctly scoping which resources any remediation action (LLM-generated or otherwise) should touch, and verifying its result against the actual violated signal rather than a proxy for it.

H. Empirical Studies of Cloud and Cross-Layer Failures

Gunawi et al. [14] show that cloud-system failures concentrate in the interactions between components rather than within them. The twelve defects catalogued in Section VI-B are, in aggregate, an instance of that finding at the remediation-automation layer specifically: every one of them lived at a seam between two independently well-documented components (Prometheus query semantics and Kubernetes' backoff behavior; Helm's history ordering and Go's sort package; Alertmanager's label precedence and the operator's alert parser; Go's goroutine model and a shared incident struct), not inside any single component's own logic.

IV. System Design

A. Self-Maintaining Dependency Graph

Batch-rollback scoping requires a "who calls whom" graph. A hand-maintained edge list is a standing maintenance liability: a new call path silently does not participate in batch rollback until someone remembers to edit the graph and redeploy the operator — and, auditing our own hand-written seed against this project's actual code, we found it had already happened: the API gateway proxies directly to all three backend services, but the seed graph only declared a gateway→order-service edge, omitting two real, live call paths (gateway→inventory-service, gateway→payment-service).

We replaced the hand-written seed with one generated by a static scanner (tools/depscan) that parses every service entry point with Go's own AST tooling and extracts an edge wherever code references a <Name>ServiceURL configuration field — a naming convention the codebase's configuration package already enforces for every cross-service dependency, regardless of whether the call is made directly (an HTTP client construction) or indirectly (a reverse-proxy route table entry), since both forms reference the same named field. The generated seed is verified in continuous integration: a build fails if the committed seed differs from a fresh scan, converting "new call path doesn't participate in batch rollback" from a silent gap into a build failure.

This generated seed forms the floor of a live graph that polls Jaeger's dependency-aggregation API on a fixed interval and merges observed edges on top of it (Section III-E); the seed is never replaced outright, so a known relationship cannot vanish from the graph merely because traffic was briefly quiet during the exact window — an active incident — when the coordinator needs it.

B. Dependency-Aware Batch-Rollback Coordinator

After a primary rollback succeeds, the coordinator consults the dependency graph for the failed service's direct callers and callees (transitive closure is deliberately excluded, since coupling weakens with distance) and rolls back any peer whose current revision was deployed within a configurable batch window of the primary's faulty revision — the operational signature of "released together." Each peer rollback claims the same atomic per-service execution gate used by alert-driven recoveries, so a peer already rolled back by its own incident is skipped and batch expansion never recurses.

Reviewing this coordinator against its own test suite and live-fault-injection history for this paper surfaced two further defects, both newly fixed in this work. First, the execution gate was claimed before the coordinator confirmed a healthy rollback target existed; if no target was found, the peer's execution slot was consumed anyway for a full cooldown window, incorrectly suppressing that service's own next legitimate alert-driven recovery even though no rollback had actually been attempted. The fix reorders target resolution before gate acquisition. Second, a peer rollback was reported successful the instant the Helm SDK call returned, with no health check at all — the same false-success mode already known for primary rollbacks (Section IV-C) had not been inherited by the peer path. The fix adds the same post-rollback verification used for primary rollbacks, and records peer outcomes to the same audit tables used for MTTR reporting, which had previously only logged peer outcomes to a free-text incident timeline.

C. SLO-Aware, Two-Signal Verification

Pod health alone is a false signal after a rollback lands on a revision with a latent fault: injected pods answer liveness/readiness probes with 200 regardless of whether they still serve the actual injected fault. Verification therefore requires two independent signals to converge: Kubernetes pod/deployment health, and confirmation, via a live Prometheus query, that the alert which triggered the incident has itself stopped firing. A rollback that lands on a still-faulty revision now fails verification and the executor walks further back through release history within the same incident, rather than reporting a false success.

D. Rollback Safety for the Healer's Own State

We distinguish two different rollback-safety questions that are often conflated. First: what happens to the healed services' data on rollback? In this system the three business microservices hold no persistent store at all — their repositories are in-memory, thread-safe maps — so a Helm rollback cannot lose or corrupt their data, because a pod restart already discards it regardless of which revision is live. Second, and distinct: what happens to the healer's own persistent state — here, a Postgres-backed incident/decision/rollback audit trail — if the healer's own Helm release is itself rolled back to a build older than a schema change that already ran? This is the one place in the system with a genuine, persistent schema, and, before this work, its migration mechanism was an unconditional list of CREATE TABLE IF NOT EXISTS statements with no version tracking at all.

We replaced this with a versioned, forward-only migration runner following an expand/contract discipline [19]: additive changes (new nullable columns, new indexes) are never marked breaking; a migration that drops, renames, or otherwise changes a column or table in a way an older binary's explicit column-list queries cannot survive must be marked breaking. A startup compatibility guard then refuses to boot if the database carries a migration marked breaking whose version exceeds what the running binary's own code understands — precisely the fingerprint of the healer's own release having been rolled back past a schema change its code no longer matches. This converts a silent data-corruption or cryptic-SQL-error risk into a loud, actionable startup failure, mirroring, one layer down, the same "verify the actual signal, don't trust an easy proxy" discipline behind Section IV-C.

B. MTTR Definition

MTTR is measured as wall-clock time from the fault-injecting helm upgrade call (t0) to the first instant both verification signals (Section IV-C) hold simultaneously (t1): pod/deployment health and the triggering alert reporting resolved in Prometheus. This dual criterion is deliberately stricter than a single readiness bit, for the same reason given in Section IV-C — it avoids crediting a recovery before the system is genuinely healthy against the metric that was actually violated.

We note, in the interest of the same version-pinning rigor this paper argues for, an inconsistency found while compiling this list: the Jaeger image tag differs between the Kubernetes manifest (1.60) and the local Docker Compose environment (1.50) — itself a small, honest instance of the reproducibility gap this section exists to close.

D. Honest Statistical Scope

Each scenario in Table II below reflects one to two live repetitions against a real cluster, not a replicated statistical sample. This is explicitly insufficient to support a significance claim, and we do not make one: every MTTR figure in this paper is reported as an illustration of mechanism (which layer of the pipeline dominates recovery time), not as a measured effect size. Raising replication to a level that could support confidence intervals and a non-parametric significance test (e.g., Mann–Whitney U) per scenario, and decomposing MTTR into detection, decision, and execution sub-intervals, is stated explicitly as future work (Section VIII) rather than implied to already be present.

Beyond the individual fixes, RQ3 asks whether these defects cluster. They do, along one clear axis: seven of twelve (F1, F2, F3, F6, F7, F9, F12) are instances of the same underlying pattern — a decision made against state that looks current but is stale, ambiguously ordered, or concurrently mutated (a superseded-but-not-yet-marked Helm revision, an unaggregated per-pod metric series, a non-atomic cooldown check, a wrong label riding along on a shared metrics series, lexicographic-not-numeric history order, a gate claimed before its precondition is confirmed, and a struct mutated from two goroutines at once). None of these defects is inside any single component's documented behavior; every one lives at a seam between two independently correct components, echoing the general finding of [14] at the remediation-automation layer specifically.

One further defect, identified while auditing target selection for this paper and not yet fixed, is reported here for the first time. F1's fix skips any candidate revision whose configuration is identical to the current (faulty) revision — but only the current one. If a rollback's target is itself later found faulty (verification fails, Section IV-C) and the executor retries, it re-resolves the target from scratch; because the config-equality check compares only against the revision it is now leaving, not against every revision already tried within the same incident, the original faulty revision can pass that check again on a subsequent attempt and be re-selected — walking sideways back into the exact fault the incident began with, rather than genuinely further back through history. We surface this as a concrete, actionable open item rather than deferring it to a vague "future work" line.

VII. Threats to Validity

A. Construct Validity

MTTR is operationalized as the dual pod-health-and-alert-cleared criterion of Section V-B, chosen to avoid crediting recovery before the actually-violated signal has cleared. Batch membership ("were these two services released together?") is itself only a construct — approximated by deploy-timestamp proximity within a configurable window — rather than an explicit, ground-truth release identifier; Section VIII discusses this directly as an open threat rather than treating the current heuristic as a settled definition.

B. Internal Validity

S4 (combined error-rate and latency injection) was excluded from Table II because it was directly contaminated by residual cooldown state from the F1–F3 oscillation testing that immediately preceded it — the decision engine correctly answered "wait," but the scenario's own result was not independently interpretable; we report this exclusion rather than omit it silently. Separately, F12's discovery has a retrospective internal-validity implication: some portion of this project's earlier "environmentally flaky" test observations, made before the race detector was run against the full concurrent test suite, cannot now be distinguished with certainty from undiagnosed instances of the exact same race, and should be treated with corresponding caution.

C. External Validity

Evidence comes from a single minikube cluster running three deliberately simple, synthetically-instrumented microservices with fault injection via Helm value overrides. Absolute MTTR magnitudes will differ on managed clusters, larger topologies, and real workloads with real traffic-sampling behavior. The mechanistic claims — that detection latency, not operator decision time, dominates recovery for level-triggered faults; that verification must check the actual signal, not a proxy; and that a healer's own state needs the same rollback discipline as the systems it heals — depend only on the presence of a windowed-evaluation alerting layer and a persistent audit store, both standard in Prometheus/Postgres-based operational stacks, so we expect the qualitative findings to generalize even where specific timings do not.

D. Statistical-Conclusion Validity

As stated in Section V-D, every MTTR figure in this paper rests on one to two repetitions. We treat the reported numbers as case-study evidence for mechanism, explicitly not as a statistically supported effect-size claim, and we do not draw any conclusion in this paper that requires the latter.

VIII. Discussion and Limitations

Several open items follow directly from Sections VI–VII and are stated here as concrete future work rather than general caveats. Batch-window membership should move from timestamp proximity to an explicit release identifier — e.g., a CI-stamped label shared by every Helm revision deployed in one release train — closing the construct-validity gap of Section VII-A. The live dependency graph's trace store is in-memory only (Section V-C); a pod restart silently discards every non-seed edge, and the next refresh cycle rebuilds the graph purely from whatever traffic happens to occur afterward. Moving to persistent trace storage, and separately adding an edge-confidence/decay model instead of a hard in-or-out-of-window cutoff, would close this without changing the coordinator's logic. Batch-peer rollback and verification currently run sequentially, one peer at a time; for n co-released peers this can add up to n times a single verification timeout to an incident's total settle time, even though it no longer affects the primary service's own measured MTTR (Section VI-A already reflects this separation). Parallelizing peer processing, and decoupling it from the primary incident's terminal state entirely, is a bounded, well-scoped fix. The target-selection double-rollback edge case (Section VI-B) needs the config-equality check widened from "differs from the current revision" to "differs from every revision already attempted within this incident." The suppressed-recovery exposure (F5) needs either an internal reconcile loop that re-evaluates gated incidents once their gate expires, or a materially shorter Alertmanager re-notification interval for the affected route. None of these are deferred as unexamined; each has a stated, concrete design already sketched above.

IX. Conclusion

Automated rollback that only ever considers the one service an alert names is solving half the problem: microservices are released in batches, and healing one member of a batch while leaving its contract-partners on the old assumption is not a complete recovery. This paper shows that extending rollback scope to co-released peers is buildable without reintroducing the oscillation that motivated per-service cooldowns in the first place, provided the same execution-gate and two-signal-verification discipline used for a single service is applied uniformly to every peer — which, audited honestly, it initially was not (F9–F11). It shows that a healer's own persistent state needs the identical rollback-safety treatment as the systems it protects, not an implicit assumption that its own schema is always forward-compatible. And it shows that live fault injection against a real cluster, paired with static analysis and a race detector run deliberately rather than incidentally, continues to surface real defects even in a system that has already been through several rounds of exactly this process — the twelfth defect in this catalogue was found auditing the mechanism meant to prevent the first three. Where this paper's own MTTR evidence is thin, we have said so directly rather than let a case study read as a benchmark; the detection-dominated recovery pattern it does support matches the mechanism reported for single-service systems, and nothing about dependency-aware batch rollback changes that mechanism — it only changes how much of the system a single alert is able to heal correctly.
